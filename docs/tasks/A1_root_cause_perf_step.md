# A1 根因定位报告：连续负载 ~2 分钟后吞吐腰斩（任务 #137）

**日期**：2026-09-30
**状态**：根因已确认（双向判别实验通过）
**结论先行**：**不是 botflow 代码缺陷，是 mq3 测试机的 GCE `e2-medium` 突发机型 CPU token bucket 节流。** 压测满载把 2 个 vCPU 打到 100%（瞬时 2.0 核），约 115 秒后 token 耗尽、被宿主机强制节流回基线 **1.0 核**，可用 CPU 减半 → 吞吐 80→40 rps。「每请求 CPU 翻倍」是**记账幻影**：guest 内 ktime 家族计数把 vCPU 停摆时间记成"在跑"。

---

## 一、根因机制（e2-medium burstable）

mq3 = GCE VM（`projects/579135669953/machineTypes/e2-medium`，zone `asia-east2-a`，kernel 6.17.0-1022-gcp）：

- **2 vCPU 共享 1 物理核 SMT**（`thread_siblings_list = 0-1`），每 vCPU 基线 50% → **合计基线 1.0 核**；
- 每 vCPU 可突发到 100%（合计 2.0 核），token bucket 满桶约支撑 **~120 秒满载**；
- token 耗尽后**由宿主机按时间片 deschedule vCPU**（非 guest 内 cgroup 节流），实测 duty ≈ 50%；
- 该节流**不走 KVM steal MSR** → guest `/proc/stat` steal 恒 0.2-0.7/s 不涨；
- token 恢复需 CPU 低于基线（停载后数十秒即恢复快相，与 s5b A/B 复测吻合）。

文献佐证：Google 官方定价页（E2 shared-core：e2-medium 每 vCPU 50%、可突发 100%）；IC2E'25 论文实测 e2-medium 满桶 200% 约 120s、节流回 1.0 基线、token 按 (usage − baseline) 消耗。

## 二、证据链（R5–R13，共 9 轮复现 + 3 轮判别）

### 1. 阶跃本身（9/9 复现）

所有饱和压测（c8/c32、chat/stream、py-spy 开关、外部 ping 开关）均在 **t+105~150s** 从 ~80 rps 阶跃到 ~40 rps，`n_err=0`，慢相长期平台不继续劣化。阶跃时刻与并发数无关（c8=c32）→ 排除应用层并发累积类假设。

### 2. 三家族计数器分裂（决定性物理证据）

t+130s 起同一 10s 采样窗内同时发生：

| 计数器家族 | 代表 | 快相 → 慢相 | 含义 |
|---|---|---|---|
| **tick 家族**（vCPU 执行才推进） | jiffies busy、`/proc/stat` user、LOC 定时中断、cgroup `usage_usec`、NIC/RES/TLB/CAL 中断、ctx-switch | 140→66 /s、LOC 1620→850 /s、1.40→0.71 MCPU-s/s、5.2K→2.3K /s | **全部 ≈ 0.5×**：vCPU 物理执行时间减半 |
| **ktime 家族**（墙钟推进就记账） | gw `schedstat`、gw `utime`、perf task-clock、标定循环 CPU-s | 恒 1.045 核 / 2.000 CPU、同工作量 7.5→15.1s | **恒定**：停摆 gap 被记成"在跑"（幻影时间） |
| **外部真值** | 本地 ping RTT（R10b，231 样本）、本地墙钟 | 间隔恒 2.54-2.78s 零超时尖峰、dMono/dReal=1.0000 | **guest 网络与外部时钟全程正常** |

- **Σpid utime（700/5s）> 机器总忙（355/5s）** 的物理矛盾 = ktime 幻影记账的直接推论；
- idle **不升反持平**（53/s 不变而 busy 腰斩）→ 排除"负载侧变化"（若请求变慢，idle 必上升补偿）；
- `steal` 恒 ~0.3/s 不涨、dmesg 无 live migration/clocksource 切换、`cpu MHz` 恒 2199.998、cgroup `cpu.max=max`/`nr_throttled=0`、perf PMU 禁用但 task-clock 恒 2.000 → 全部排除：宿主争用 steal 记账、迁移、降频、guest cgroup 节流。

### 3. 标定循环（R8）：同工作量 CPU-s 恰好翻倍

30M 次纯计算循环，wall/CPU/sched 三点在快慢两相：4.30s（空载）→ 7.50s（快相）→ **15.10s（慢相，正好 2×）** → 5.32s（停载后恢复）。**同一段代码的 CPU 时间翻倍，代码本身零变化** → 排除任何"代码路径累积劣化"解释。

### 4. 双向判别实验（R11 vs R13）

| | R11（c8 不限速） | R13（c8 限速 35 rps） |
|---|---|---|
| CPU 需求（busy） | **140/s = 1.4 核 > 基线 1.0** | **77/s = 0.77 核 < 基线 1.0** |
| t+120s 阶跃 | **复现**（75.5→38 rps） | **不出现**（300s 全程 32-37 rps 平稳） |
| LOC 后/前 | **0.496**（腰斩） | 无腰斩（busy 后/前 1.0×，tickTot 恒 188-190） |

**CPU 需求 > 基线 → ~115s 必阶跃；需求 < 基线 → 300s 永不阶跃**——token bucket 的核心可证伪预测双向成立。

### 5. 对旧假设的处置

| 旧假设（报告 §五/§六） | 判定 | 依据 |
|---|---|---|
| langgraph `merge_configs` config 体积累积 | **证伪** | R5b 探针：tick 总耗时两相持平 0.43s/10s、merge 每调用恒 ~14µs、GC 恒 0.4s/10s——已知 Python 路径无一翻倍；py-spy 相对占比变化是**分母（vCPU 执行时间）减半**的组成漂移 |
| dedup 写路径解释一半衰减 | **证伪** | 流式跳过 dedup 同样衰减；R13 限速下 dedup 照写不误但无衰减 |
| GC / native 帧 | 证伪 | 探针 GC 恒定；且硬件中断计数腰斩无法由 GC 解释 |
| py-spy 扰动 / 进程年龄 / 上游 | 早已排除 | 见 §五原记录 |

§六 py-spy "pregel +5.9pp、merge_configs self +2.0pp" 重新解读：**采样分母是幻影恒定的 ktime、分子构成随 tick 家族减半而漂移**——相对占比差分在两相间不可比，非真实路径增长。

### 6. R12 部分回填定量实验（已收口，区分 token 数量模型 vs 连续时长上限）

设计：90s 满回填 → 150s 负载 A → 30s idle → 240s 负载 B；两段各独立记 rps 时间轴与逐窗 tick/ktime。

结果（loadgen 相位 JSON + r12_probe.jsonl）：

| 段 | 前置 idle | burst 持续 | rps（burst→节后） |
|---|---|---|---|
| A | 90s（满桶） | **~120s 阶跃** | ~67-82 → ~37.6 |
| B | 30s（部分回填） | **~60s 阶跃** | ~65-75 → ~34-39 |

- B 段只回填 30s，burst 窗口从 120s 缩到 ~60s（≈一半）→ **确认「token 数量模型」**：burst 预算可随 idle 回填，且**回填比例近似线性**（30s 得 ~50% 时长）。
- **排除「连续突发有硬 120s 上限、与 idle 无关」**：若硬上限成立，B 段也应在 ~120s 才阶跃。
- 物理佐证（r12_probe 覆盖 B 段）：B 前 50s busy≈140/s、LOC≈1700/s（满 burst），B t+60s 起 busy 腰斩到 ~73/s、LOC 降到 ~900/s（与 R11 慢相同相位一致）→ 节流机制在两相间完全一致，差异仅在"burst 窗口长度随回填量变化"。

**对规避方案的含义**：压测间静置 ≥90s 可满桶恢复，≈120s 饱和 burst；静置不足则下一轮 burst 窗口按比例缩短（如 30s idle → ~60s burst）。这与 s5b 实测「停载数十秒即恢复快相」吻合。

### 7. 尚存的未定细节（诚实标注，不影响结论）

- 节流 duty 精确值（LOC 0.52×、busy 0.47×、标定 2.0×）指向 ~50%，但 busy 0.47 与"基线 1.0 / 瞬时 1.4"之比 0.71 不完全一致——可能因慢相需求本身下降（rps 腰斩后请求变少）+ duty 50% 双重作用，未单独定量。
- 生产 `api.vxquant.com` 实例机型**未确认**（非 mq3）；若生产也是突发机型，真实流量尖峰同样会触发节流——需在 A2 核查（建议 `curl metadata .../machine-type`）。

## 三、影响面

1. **代码零缺陷**：botflow 无需为此改任何代码；`tracemalloc` 定位累积对象（A1 原方案）不再需要。
2. **压测报告 §五/§六 结论需更正**（本任务收尾项）：`docs/perf-load-test-2026-09-30.md` 的"根因假设"与"建议 #1"应改写。
3. **§七建议 #1「稳态吞吐 40→79 翻倍」的收益预期作废**——40 rps 是机型基线，不是应用瓶颈；原 #2-#7 已重排为 **#1-#6 优化建议依然有效**（降低每请求 CPU 仍有价值：同样的基线 1.0 核能扛更多 rps）。
4. **A2/A3 任务内容变更**：从"修代码"变为"规避方案 + 验证标准"。

## 四、建议（A2 展开）

- **测试环境**：压测机换 `e2-standard-2`（独享 2 核）或在 e2-medium 上把饱和压测时长限制在 <100s / 限速 ≤ 基线（R13 模式）；每轮压测间静置 ≥90s 等 token 回填。
- **压测方法**：报告中所有长跑数据需标注机型节流影响；以后压测报告附 `/machine-type` 与逐窗 busy 校验。
- **生产**：核查 api.vxquant.com 机型；若为突发型，评估真实流量尖峰下的等效基线。
- **应用侧**（可选，非根因修复）：限速/背压（§七 #4/#5）恰好能防止"自伤式"满载触发节流。
